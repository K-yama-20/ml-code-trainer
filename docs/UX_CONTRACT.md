# DrillのUX契約

この文書は、実装や教材を変更するときに守る学習体験のルールを定める。Phase 1以降のレビューでは、自動テストだけでなく、初学者が説明なしで操作できるかを確認する。

## 1. 学習の終了は学習者が決める

- ステージ達成、目標問題数への到達、現在のキューの末尾は、セッションを終了する理由にしない。
- キューが尽きたら、既存の履歴・進捗と条件を使って次の問題を補充する。問題数の目標は上限ではない。
- 通常の概念演習はGuided→Partial→Independentと進む。Independentの練習後は関連概念または復習へ進む。
- 「このステージを練習」の指定は概念演習の開始点であり、同じステージへ閉じ込める指定ではない。
- Customで明示したライブラリ・ステージの範囲は尊重する。選んだ範囲の別入力・別問題で練習を続けられる。
- 次問が本当に用意できない場合は、その場に理由と別の演習への選択肢を表示する。ホームへ自動転送しない。
- 正解だけで次へ自動遷移しない。「次の問題」を押して進む。
- 「中断して保存」を選んだ場合のみ、保存してホームへ移動できる。「演習を終了」は明示的な操作で行い、終了画面を表示する。

### 混ぜてはいけない状態

| 状態 | 意味 |
|---|---|
| ステージの認定条件 | 異なる2つの問題familyをヒント・模範解答なしで正解。Independentは正式なサーバー検証も必要 |
| 練習を次へ進められる条件 | 現在の回答を答え合わせして正解、または明示的にスキップ |
| セッションの終了 | 学習者が終了操作を選んだ状態 |
| 目標問題数 | 取り組む量の目安。達成しても継続できる |
| キューの枯渇 | 次の問題を選んで追加するタイミング |
| 画面遷移 | サーバーが返す次のitemへ移動。キュー長から終了を推測しない |

Independentのブラウザー暫定正解で練習を先へ進めても、正式な習得認定にはしない。直接Partialから始める場合も、練習順と、前段を含む認定の条件は区別する。

## 2. 問題の目的は最初に分かる

解答前の中心情報は「すること」「求める結果」「回答する場所」の3つとする。

- 初見で理解できる短い問題文、具体入力の意味、出力の条件を示す。
- 問題の説明を、学習のポイント・巨大なテスト一覧・装飾カードで押し下げない。
- 「学習のポイント」に相当する解き方の説明は、正解を記録した後に表示する。
- 具体入力はコード欄で最初から読めるようにする。公開ケースの詳細な一覧は、解答後の「動作確認」として扱う。
- 誤答時は修正の手掛かりを出す。完成解法を自動で開いて、ヒントなしの達成と混同しない。
- 新版の出力予測は表示した1入力について答える。正解を初期表示しない。旧版の式入力との互換性は保持する。

## 3. 解答欄と編集範囲を明確にする

| 問題形式 | 必須の案内・表示 |
|---|---|
| 穴埋め | 提供入力を固定し、コード構造で示された空の範囲だけを編集可能にする |
| 部分記述 | resultの右側や、修正する呼び出しを指定する |
| 自力記述 | 具体入力とresultへの代入を示す。関数が学習目標の場合のみシグネチャを示す |
| 出力予測 | 値・shapeの専用欄を使い、関数定義やreturnは入力させない |
| バグ修正 | 実際の修正前コードを提示し、調べる処理や範囲を示す |

予測値は既存の実行・採点経路へ接続するために関数へ包んで保存できる。ただし、既存のコード下書きを黙って値へ変換したり、消したりしない。旧下書きはコードとして開けること。

## 4. 主要操作を状態に合わせる

| 状態 | 主操作 | 補助操作 |
|---|---|---|
| 解答前／回答を変更した | 答え合わせ | 実行のみ、必要なときにヒント |
| 採点中 | 中止 | 回答は保持。次問移動・終了で処理を競合させない |
| 正解を記録した | 次の問題 | 解き方や模範解答を確認 |
| 不正解 | もう一度答え合わせ | 動作確認・ヒント。明示的なスキップはメニューから |
| 実行のみで合格した | 答え合わせ | 未記録であることを結果に明示 |

同じ領域に主ボタンを複数並べない。RunとSubmitの内部の違いを維持しつつ、学習者には「試す」と「答え合わせして記録する」の違いとして伝える。

DrillではCtrl/Cmd+Enterで答え合わせ、Ctrl/Cmd+Shift+Enterで次問へ進む。Alt/Option+Hでヒント、Alt/Option+Jで模範解答を開閉する。従来のCtrl/Cmd+Alt+Enterでの実行とAlt/Option+Nでの次問移動も利用できる。IME変換中や長押しの繰り返しでは起動しない。

## 5. 正誤の結果から学べる

- 日本語の判定と記録済み／未記録を示す。内部のverificationは保持する。
- 公開ケースの期待値と実値を比較できる。配列はshape、必要なdtype、Pandasは列名・index・欠損を落とさない。
- 非公開ケースの入力・期待値・実値を、比較表示へ混ぜない。
- 誤答の案内は、その問題で確認すべき点を示す。実際に検知していない原因を断定しない。
- 正解後は、なぜその処理でよいかを説明する。ヒントの単なる再掲で済ませない。
- 中止した実行には中止の表示を出す。前回の正解を今回の結果として表示しない。
- 回答を編集したら以前の結果と区別し、古い結果をそのまま提出しない。

## 6. 回答と記録を失わない

- RunだけではAttempt・習熟度・復習予定を更新しない。
- Submitは既存のコードハッシュ、実行mode、所有者確認、冪等性を維持する。
- 不正解、実行エラー、タブ切替、次問移動でも回答を保持する。
- 初期状態へ戻す操作は同名関数の追記にしない。変更前の回答を戻せるようにする。
- 保存競合を無条件の上書きで解決しない。
- 次問取得の再送で同じ末尾を何度も追加しない。古いitem・下書き・Attemptを削除したり採番し直したりしない。
- ヒント・模範解答を見た事実は保持する。新しい独力確認は新しいitemとして行う。
- 教材変更前の版・seedを保存する。旧提出を新教材・新採点条件で黙って上書きしない。

## 7. 実行できる状態を正直に示す

Sandboxを使えない環境では、取り組み前に知らせる。環境の設定失敗を学習者の誤答として記録しない。読んだり編集したりできる状態と、実行できる状態は分ける。

モバイルでは問題と回答を切り替えても回答を失わず、編集中にも問題の要約を参照できる。実機キーボードを表示した状態の操作性は、人間による確認項目とする。

## 8. 変更時の確認

自動確認は `test_continuation.py`、`test_api.py`、`test_grading.py`、`drill-phase1.spec.ts`、`trainer.spec.ts` を中心に行う。特に20問を超えた継続、通常の概念画面からの2問後の進行、正式／暫定認定の区別、旧版、誤答後の回答保持を省略しない。

自動テストを通過しても、「初学者が何をすればよいか説明できる」「ヒントを読んで自分で次の一歩を選べる」の確認は完了しない。ユーザーテストで検証する。

## 9. 具体入力方式の契約（2026-11追加）

- 基本操作は、具体的な入力コードとresultへの処理を隣接表示する。採点用のsolveを初学者へ要求しない。
- workspaceの提供コードと、Draft・Attemptに保存する解答コードを区別する。提供コードを誤編集できる入力欄にしない。
- Guidedの初期画面は空欄だけを編集可能にする。本文に`___`、`TODO`、専用の背景色を表示しない。初期カーソルは編集開始位置に置く。保存済みの別解や削除後の空欄はその状態で復元する。
- 単一Monacoモデルが入力とUndo/Redoを管理する。固定範囲をまたぐ編集は適用前に拒否する。通常の入力、IME、貼り付け、複数行編集のたびに文書を書き直さない。
- 準備済みのブラウザ実行では起動表示を出さない。ランタイムを再利用する場合もケースの変数は毎回作り直す。ファイルや実行環境に触れるコードを実行した後はWorkerを破棄する。
- Partial・Independentも具体入力を残す。書く範囲と応用する入力条件を広げる。
- クラス内のforwardや、関数定義そのものを学ぶ構造を消さない。具体入力と呼び出し例を添える。
- 結果のない出力パネルで初期画面を占有しない。通知・エラー・キャンセルの結果は隠さない。
- scriptの正式採点は問題版のexecution契約だけを使い、クライアントが持つ入力・定義を採点の根拠にしない。
- 表示入力のコピーや入力の上書きで正式な正解を作れないよう、異なる入力と入力保護を検証する。無関係なAPIの使用を採点へ追加しない。
- 正式採点の公開入力と非公開入力は別Sandboxで実行し、非公開側のstdout・エラー詳細を返さない。
- 実行方式が利用できなくなっても、記録済みの正解から「次の問題」へ進むことを妨げない。
- 新版の導入時は旧定義を保存し、旧セッションのコード・版・入力seedを変更しない。旧版の画面と採点も回帰確認する。

追加の確認対象はtest_concrete.py、AnswerWorkspace.test.tsx、concrete.spec.ts、実Pyodideのbrowser-content.spec.ts。Modalのクラウド接続と課金を伴う実行は別途検証し、ローカルの疑似Providerでの合格と混同しない。

## 統一エディタの最新契約

2026-11の統一Monaco改修では、上記の別領域や段階的ヒントに関する旧表示規則を次の仕様へ更新する。

- コード形式は1つのMonacoモデルで入力と解答を表示する。preと別エディタで疑似的に一体化しない。
- 固定入力・指定した骨格をBackspace/Delete/貼り付け/Undo/Redoで変更してはならない。拒否した変更は下書きに保存しない。
- ヒントと模範解答は課題の下へ常設し、初期は閉じる。ヒントは1つ。模範解答は正解前でも開ける。
- 閲覧記録・習熟度への反映は維持し、閲覧だけで提出・解答欄上書きを行わない。
- 初期画面から冗長な編集案内・出力仕様カードを除く。正解後は判定・件数・次の問題を中心にする。
- テーマのデフォルト・色変数・選択保存は変更せず、両テーマで同じ情報構造を使う。
- 統一表示にしても採点には解答部分だけを渡し、正式入力は信頼する問題定義から供給する。
- 通常のセッション継続・認定基準・復習・履歴・保存競合のルールを維持する。
