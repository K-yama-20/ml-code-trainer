# Drill UX改善 Phase 1 実装報告

## 変更した体験

解答前は、問題の目的、入力と返すもの、編集する場所を中心にした。「学習のポイント」のカード、目立つ公開テスト一覧、バッジ・variant・英語の装飾見出しをDrillの初期画面から外した。問題の説明と同じ編集案内は、PCでは回答欄の上へまとめ、狭い画面では問題側にも示す。

主操作は「答え合わせ」と、正解を記録した後の「次の問題」。答え合わせは既存のSubmit、補助の「実行のみ」はRunを使う。Runで合格しても未記録であることを明示し、未提出のまま正解後の次問ボタンが出る状態をなくした。スキップ、中断、終了は演習メニューから明示的に選ぶ。

正解後は解き方を表示する。不正解では問題別の確認事項と、公開入力の期待値・実値を比較できる。Pandasはindex・列名・欠損値、配列はshapeと必要なdtypeを表示する。中止後は前回の正解を出さず、回答を保持した旨を表示する。

## 「2問でホームへ戻る」の原因と修正

旧実装では、概念開始時に現在のステージの2問だけがキューへ入り、画面のnext処理がキューの最後でcompleteを呼んでホームへ移動していた。ステージ判定の処理自体がホームへ戻していたわけではない。概念ページのステージ指定も、2問のCustomセッションを作っていた。

| 論点 | 修正後 |
|---|---|
| ステージ進行 | family単位の2問、ヒント・模範解答、Independentの正式検証という認定条件を維持 |
| セッション終了 | 自発的な終了操作のみ。キュー末尾でcompleteしない |
| 目標数 | goal_countとして継続状態に保存。Dailyの既定は設定された目標、明示した件数はその演習の目安 |
| キュー末尾 | advance APIが現在の進捗と条件を読み、次の2問を追加 |
| ルーティング | 返された次のitemへ移動。次がなければ理由と別の演習をその場で表示 |

通常の概念演習はGuided→Partial→Independent→関連概念／復習へ進む。概念ページのステージボタンは開始点として扱う。Customで選んだ分野・ステージの範囲は維持する。ヒントで解いたため認定条件が未達の場合は、新しいitemで確認できる。seedは切り替えるが、全問で公開入力が変わるわけではないため、「必ず別の入力になる」とは案内しない。

Dailyは、固定比率で別分野を散らすより、現在の概念・前提知識・復習を優先し、少数ずつ補充する。開始画面の旧40%／40%／20%という説明も、新しい選題方針に合わせた。

Independentのブラウザー暫定正解が2問揃った場合も、練習は次へ進める。ただしmasteryを正式認定へ繰り上げない。認定と練習順を分けた。指定してPartialから始めた場合も、未達のGuided認定を勝手に付与しない。

## 実装箇所

- [learning.py](../apps/api/app/learning.py)：継続候補の選定、前提を考慮したDailyの開始、版に対応した進捗更新。
- [main.py](../apps/api/app/main.py)：advance、最終提出の再表示、目標数と継続状態の保持。
- [db.py](../apps/api/app/db.py)：追加テーブルSessionFlow。旧item・Attempt・下書きの削除や採番変更はしない。
- [Drill.tsx](../apps/web/src/pages/Drill.tsx)：保存・Run・Submit・遷移の制御。[DrillView.tsx](../apps/web/src/pages/DrillView.tsx)と[Drill.css](../apps/web/src/pages/Drill.css)：状態別UI。
- [answer.ts](../apps/web/src/features/answer.ts)：予測値を既存のsolve形式へ包む変換。旧コード下書きはコードのまま開く。
- [ResultValue.tsx](../apps/web/src/components/ResultValue.tsx)：表・配列・スカラーの表示。[worker.py](../apps/api/app/worker.py)／[grading.py](../apps/api/app/grading.py)：公開分だけの比較情報。
- [drill_phase1.py](../content/drill_phase1.py)：代表15問の著者定義。[compile_content.py](../scripts/compile_content.py)から適用する。
- Homeの再開件数の表示と、概念ページの演習開始種別を小さく修正した。他ページのデザインを広く変更していない。

次問取得はfrom_item_idに対して永続的に同じ次問を返す。通信再送でキューを重複追加しない。旧セッションに継続状態がない場合も復元する。旧ステージボタン由来と判断できる、単一概念の旧Customセッションは自然な段階進行として引き継ぐ。

## 解答欄と教材

- 穴埋め：空欄を強調。
- 部分記述：変更する式・引数を回答欄の上へ表示。
- 自力記述：関数シグネチャを残し、関数内に処理を書くと説明。
- 予測：数値・shape・値のための専用入力欄。関数定義は不要。
- バグ修正：実際の誤コードと修正対象を提示。

15問を@2へ更新した。各分野3問、各ステージ5問で、予測2問とバグ修正3問を含む。タイトル、目的、入力・戻り値、編集案内、3段階のヒント、解説、具体的な誤り例、誤答時の確認事項を個別に記述した。

PY03-04とNP06-04は固定された入力の予測へ整理し、新版は1つの観察を採点する。NP05-01の最初の公開例は小さな手計算できる配列にした。模範解答のアルゴリズムは15問とも変更していない。他の165問は両seedとも、旧データとの全フィールド比較で一致する。

旧@1はseed42／99の両方を [content/versions](../content/versions) へ保存した。旧履歴の問題、解説、ケースを引き続き参照できる。予測の回答値も既存のコード形式で保存するため、現在の履歴画面では包んだsolveコードが表示される。この履歴表現の整理は今後の課題である。

記述基準は [CONTENT_STYLE_GUIDE.md](CONTENT_STYLE_GUIDE.md)、守る体験のルールは [UX_CONTRACT.md](UX_CONTRACT.md) を参照。

## 検証結果

| 確認 | 結果 |
|---|---|
| バックエンド | 60 passed、外部接続を必要とする2件はskip |
| フロントエンド | 13 passed |
| Playwright | Phase 1の7本＋既存回帰6本、計13本passed。最終の利用可否・比較表示条件の修正後、関連3本も再確認 |
| 静的検査 | TypeScript、本番ビルド、ESLint、Ruffを確認 |
| 内容の互換性 | 165問の全フィールド一致、旧@1の両seed、新15問の両seedの模範解答を検証 |

実際のブラウザーで21問を解き、22問目へ到達した。20問の目標を越えても同じsessionのままactiveで、履歴は21件。最初の6問はGuided 2問→Partial 2問→Independent 2問で、その後は別の概念へ進んだ。[操作系列](../artifacts/ux-phase1/continuous-21.json)

正式なIndependent達成後の遷移は、完了した正式実行JobをDB fixtureで用意するAPIテストで確認した。ブラウザーの連続演習は実Pyodideを使い、暫定と正式を区別する。実Modalへのクラウド接続を行ったという意味ではない。

構文エラー、実行エラー、時間上限、実行中編集のstale表示、中止、誤答後のコード保持、下書きの再読込、ヒントの段階表示、保存された履歴、明示的な終了、実行不可の説明、モバイル幅も確認した。APIテスト用の起動処理は実DBではなくfixture内DBを使うようにした。

補助撮影と追加テストを同時実行した際には、既存のゲスト認証の同IPレート制限で429となった。並行する補助撮影を止め、対象3本を直列で再実行して通過を確認した。認証の制限自体は緩和していない。同IPで多数が同時に初期化する利用形態は今後の運用確認項目とする。

コマンド：

```powershell
apps/api/.venv/Scripts/python.exe -m pytest apps/api/tests -q
npm test
npm run lint
npm run build
npm run test:e2e:phase1
```

E2Eは専用ポート5174／8001、別DB、Playwrightの独立したブラウザーコンテキストを使う構成を用意した。既存の8000／5173を停止・再設定していない。テストや確認で作ったゲスト履歴は専用DB内にある。QA用サーバーは確認後に終了した。通常の開発環境へ反映する際は、APIを再起動して新しいエンドポイントを読み込む。

## 適用時の注意

ローカルSQLiteは追加テーブルを起動時に作成する。本番PostgreSQLでは、APIを更新する前に [202611030002_session_flow.sql](../supabase/migrations/202611030002_session_flow.sql) を適用する。既存テーブルを削除・初期化する移行ではない。フロントとAPIを揃えて更新し、旧APIのプロセスを再起動する必要がある。本番への配備は今回実施していない。

## 残っている課題と人間による確認

1. **初学者の理解**：自動テストは正解を知る操作である。課題を言い換えられるか、編集箇所が分かるか、ヒントから自分で修正できるかは、実際の初心者5〜6人程度で探索的に確認する。
2. **残り165問**：共通の抽象的ヒント、短い解説、未整理の用語は残る。予測の18問は従来の複数入力に対応する式の形式であり、固定入力の予測への個別改稿が必要。
3. **API利用の検証範囲**：出力比較や既存AST検査だけでは、apply(**config)、mergeのvalidate、分割のstratify等の実施を完全には測らない。今回は既存の正解条件を維持した。この厳格化は、別解・例外・問題版を含めた採点設計として次に扱う。
4. **実環境**：本番SupabaseのRLS・移行、実Modalの正式実行、モバイル実機キーボード・IME・タッチ・支援技術は未検証。画面幅の確認だけで実機操作に合格とはしない。
5. **履歴と長期利用**：予測値の履歴表示、未解答下書きの再発見、非常に長いセッションの一覧取得・ページ分割は今後整理する。途中終了の強制による解決はしない。

ユーザーテストでは「初回から1問を記録して次へ」「誤答を比較して修正」「ヒント後に別入力で確認」「21問目でも継続」「狭い画面で問題を参照して入力」を観察する。装飾の好みだけでなく、迷い・往復・理解の説明を記録する。
