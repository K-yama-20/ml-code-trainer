# ML Code Trainer UX・学習コンテンツ監査

監査日：2026年11月3日。対象：Pythonの基本構文・関数・リストを理解している、機械学習の初学者。

**実行して答え合わせする基盤は動作している。一方、「何を編集するか」「何を満たせば正解か」「結果をどう記録するか」の説明が分散している。全面的な配色変更より、この学習の流れと教材の説明構造を先に改善すべきである。**

確認した20件は **Critical 0件、High 8件、Medium 11件、Low 1件**。重要度は監査者による影響・復旧のしやすさの評価であり、利用者の失敗率を測定したものではない。

## 1. 調査方法と判断の限界

### 実施したこと

- 全180問について、分野・概念・ステージ・形式・初期コード・ヒント・解説・採点条件・公開／非公開ケースの構造を集計した。
- 5分野から各3問、3ステージから各5問、計15問の問題文・初期コード・全3ヒント・解説・よくある間違いを詳しく読み、実際の演習画面でも表示した。出力予測・穴埋め・自力実装・バグ修正を含む。
- 代表問を指定するための検証用セッション生成にはAPIを使い、その後のコード編集・実行・提出・ヒント閲覧等はUIから行った。初回導線は通常のボタン操作で確認した。
- Playwright 1.58.2のChromiumで、初回訪問、演習開始、コード編集、誤答、正解、提出、未提出での次問移動、終了、中止、初期コード挿入、履歴、ヒント利用後の進捗、Code Readingの回答・定義ジャンプを操作した。
- 1440×1000、390×844、768×1024の画面幅で確認し、**49枚のスクリーンショット**を保存した。[画像一覧](ux-audit/README.md)
- 指示された処理を省いた解答など6件を、既存の実行ハーネス・採点器と各問の公開2件＋非公開2件でローカル検証した。うちPD01-03は15問以外の補助確認である。

### 証拠の区別

| 記号 | 意味 |
|---|---|
| B | 実際のブラウザー操作・画面で再現した事実 |
| D | データ集計・ソースから確認した事実 |

以下の「想定影響」はHである。**初心者を被験者とするユーザーテストは実施していない。** 操作できなかった利用者がいた、迷う人が何％いる、といった主張は行わない。180問すべての構造確認と、15問の詳細な教育内容レビューも区別する。

### 環境と隔離

既存の8000／5173ポートは使用中だったため、監査APIを8001、Viteを5174で起動した。監査APIのDBは `artifacts/ux-audit-20261103/audit.db`。Viteの既存プロキシ設定は変更せず、Playwrightの監査コンテキスト内の `/api/v1/**` 通信だけを実APIの8001へ転送した。レスポンスや採点結果のモックは使っていない。操作対象は新規のローカルゲストである。

クラウド認証は未設定、`EXECUTION_PROVIDER=disabled`。PyodideによるNumPy／Pandasの実行を確認した。**Modalによる正式採点・PyTorchのクラウド実行・クラウド認証は未検証**。UX08は、この利用不可状態での画面の扱いについての指摘であり、本番環境の障害を意味しない。

スマートフォン／タブレットは画面幅の再現であり、実機のソフトウェアキーボード・IME・タッチ操作の検証ではない。スクリーンリーダー、全配色のコントラスト、複数端末の競合復旧も今回の実操作の対象外とした。

## 2. 全体評価

### 最重要基準への回答

「説明を受けずに開いて、何をすべきか理解し、コードを書き、答え合わせできるか」に対し、**監査者は一連の操作を完了できた。ただし、初学者が独力で“記録まで含めて”完了できると判断するには、次の欠落が大きい。**

1. 「実行」で緑のAcceptedになっても未提出であり、そのまま次へ進んで終了できる。2問正解して履歴0件、という状態を再現した。
2. 誤答時に自分の返した値が表示されず、Pandasの採点対象であるindexも期待値の表示から落ちる。何を直すべきか判断する材料が足りない。
3. 問題文に求める処理と採点条件の対応が弱い問題、予測と実装が混在する問題がある。
4. ヒントの段階性が弱く、問題と直接関係しない「よくある間違い」がある。複雑なMLの操作を、短い一般論だけで説明している。

### 維持したい点

- 登録を要求せず演習に入れる。実際の初回導線は `/` → `/home` → 演習として成立した。
- PY01-01など、動作・対象・順序の条件が短く具体的な問題もある。公開テストに空入力等を含む点もよい。
- 問題とエディターを並べたPC画面、パネルのサイズ調整、集中表示、実行中止が用意されている。
- 誤答後もコードが残る。未提出で終了した場合も、監査では下書きをAPIから取得できた。UX01をコード消失と混同しないこと。
- ローカル保存、API同期、リビジョンによる競合検出がある。実行中に編集されたコードの結果をそのまま提出しない保護も実装されている。
- 正式検証とブラウザー暫定結果を区別している。初回分析画面の「未測定」表示も、未学習を能力0と扱わない点で適切である。
- Code Readingは定義ジャンプが動き、不正解でも正しい選択肢と理由が表示された。[確認画面](ux-audit/22-reading-feedback-and-jump.png)
- カリキュラムの下方から概念詳細へ移動した確認では、スクロール位置3880から0に戻り、見出しも表示された。スクロール残留を問題として計上していない。

### UX01 — 実行で正解しても未提出で終了できる

**再現・事実：** NP05の概念演習を新規ゲストで開始。NP05-02、NP05-01をそれぞれ正しく編集し「実行」→Accepted→「次へ」。2問目の次でホームに戻り、履歴件数は0、現在のセッションもなし。下書きは残っていた。[実行後](ux-audit/07-run-accepted-not-submitted.png)／[終了後](ux-audit/08-session-ended-no-history.png)

**該当：** `/drill/s/:sessionId/:itemId`、[Drill.tsx](../apps/web/src/pages/Drill.tsx#L198) のexecute、L296のnext、L761のフッター。Runは進捗を変えない説明はあるが、8pxで表示される。

**想定影響：** 緑の正解表示を学習完了と受け取ると、後で記録や進捗がない理由を理解できない。コード消失ではなく、答え合わせと学習記録の操作が分離している問題である。

**改善：** 結果に「公開テストに合格・まだ提出していません」を表示。主ボタンを「答え合わせして記録」、実験用を「試しに実行」など意味で区別する。正解後に「提出して次へ」、未提出なら明示的な「スキップ」を用意し、終了時に提出済み／未提出数を示す。

**互換性：** Runを勝手に履歴へ保存する仕様変更は避ける。提出の冪等性、実行したコードのハッシュ、編集途中の結果の扱いを維持する。セッション完了と問題の提出済み状態は分けて表示する。

### UX02 — 問題文の処理要件と合格条件が一致しない

**再現・事実：** PD04-06で `return left.merge(right, on='id', how='left')` を実行すると、指定の `validate='many_to_one'` がなくても公開2/2がAccepted。[画面](ux-audit/15-missing-validate-accepted.png)。ローカルでは非公開を含む4/4も合格した。下の補助検証表参照。

**該当：** `content/catalog.py` のPY02-06・PD04-06・SK01-01・SK02-04、`content/compiled/private.json` の各ID、[grading.py](../apps/api/app/grading.py#L7)、[python.ts](../apps/web/src/features/python.ts#L139)。AST判定も指定名・属性名等の存在を見る方式で、実際の呼出し方までは検証しない。

**想定影響：** 学習者が「指示された概念を使えた」と受け取る合格と、出力が合っただけの合格が混ざる。何を習得したという評価なのかが曖昧になる。

**改善：** まず、結果が等しければ別解として認める問題と、特定APIの使い方を学ぶ問題を明文化する。前者は文を動作条件中心に直す。後者はAPI要件を表示し、目的を測るケース・構造検査を設計する。単純な名前の追加チェックだけでは解決しない。

**互換性：** 採点・教材双方への影響が大きい。PD04の重複右キーを検証するには期待例外の扱いも設計が必要で、現採点器は例外をRuntime Errorにする。旧版のAcceptedを新ルールで黙って再評価せず、問題版・採点版を保つ。

### UX03 — 入出力の表示から必要な構造が落ちる

**再現・事実：** PD01-01の期待値は行データのみで、columns・indexがない。欠損値は内部表現の文字列 `"__NaN__"`。`reset_index(drop=True)` を追加すると値は同じでも公開1/2のWrong Answerになる。[画面](ux-audit/13-pandas-index-invisible.png)。NP05-01の最初の入力は `solve(x)` で、xの定義は折り畳み内、期待値は長い小数列である。

**該当：** [Drill.tsx](../apps/web/src/pages/Drill.tsx#L499) の公開テストとL799のpretty、[runner.py](../content/runner.py#L26) の正規化形式。入力説明の生成は `compile_content.py:221` 付近。

**想定影響：** 初学者が型・軸・行ラベルを判断する前に、fixture用コードや長い数値を読み解く必要がある。表示上同じに見える値が不正解になる理由も追いにくい。

**改善：** 入力と期待出力を型に合わせて表示する。配列はshape、必要な場合のdtype、Pandasは列名・index付き表と欠損値を表示する。第1例は手計算できる小例、第2例以降や非公開は境界・ランダムケースにする。引数の型・形状・意味、戻り値、保持すべき属性を別項目にする。

**互換性：** 型別表示は既存の正規化値から作れ、比較ロジックを変える必要はない。`__NaN__` は表示だけ変換し、保存値は保持する。公開例を差し替える場合は採点ケースと版管理を確認する。

### UX04 — 誤答後に直すための比較材料がない

**再現・事実：** NP05-01で `x.mean(axis=0)` を返すと「Wrong Answer、0/2、Test 1、Test 2」のみ。実値、期待shapeとの比較、失敗箇所の説明は出ない。[画面](ux-audit/09-wrong-answer-no-diff.png)。テスト名の表示もクリック可能な詳細ではない。

**該当：** `Drill.tsx:693` 以降の結果表示、`python.ts` のResult生成、`grading.py:49`。現在の比較結果は主に合否とエラー文字列である。

**想定影響：** 文法エラーでない誤答では、試す・観察する・修正する循環を回しにくい。正解を丸ごと見ることが最短の解決策になりやすい。

**改善：** 失敗した公開ケースを展開し、「期待shape (3,)／実際 (4,)」や「indexだけ異なる」など比較を出す。「正解」「出力が違います」「実行エラー」の日本語と、違いの種類に応じた次の確認事項を示す。一般的な説明と模範解答は分ける。

**互換性：** 合否基準は変えず、公開ケース用の比較情報をResultに追加する。既存保存結果で項目がない場合も表示できる設計にする。非公開ケースの入力・期待値・実値は表示しない。

### UX05 — ヒントと「よくある間違い」の適合性が弱い

**再現・事実：** PY01-01は正の値を二乗する問題だが、誤り説明はenumerateの番号とzipの長さ。SK03-05は回帰係数だが、確率列とclasses_を説明する。第3ヒントは全180問同一、第2ヒントと解説も全問同文。[PY01の解説](ux-audit/solution-PY01-01.png)／[NP05のヒント](ux-audit/hints-NP05-01.png)

## 5. 採点条件の補助検証

すべて**ローカルで既存の `content.runner.run_payload` と `grading.judge` を使用**。公開2件＋非公開2件、現在のseed42のケースで確認した。クラウドの正式検証結果ではない。下の出力一致だけから、一般の入力に対する完全な正しさも保証できない。

| 問題 | 検証した解答・省いた要件 | 結果 | 解釈 |
|---|---|---|---|
| PY02-06 | 内部applyも `**config` 呼出しも使わず、configから直接リスト内包表記 | Accepted 4/4 | 辞書展開の学習要件を測っていない |
| PD04-06 | 左結合のみ。validateを指定しない | Accepted 4/4。ブラウザー公開も2/2 | 右キーが重複しないケースだけなので、検証機能の有無が出力に現れない |
| SK01-01 | random_state=999、stratify省略で分割し、件数を返す | Accepted 4/4 | 件数だけでは再現性・クラス比の条件を区別できない |
| SK02-04 | StandardScalerを使わず `train.mean(axis=0)` を返す | Accepted 4/4 | 値は妥当な別解。Scalerのfitを学習要件とするなら文と採点を合わせる必要がある |
| PY03-04 | ファイル操作をせず `return data` | Accepted 4/4 | 予測としては妥当。保存・再読込の実装課題として読むと矛盾する |
| PD01-03（補助） | `iloc = None` を置き、実際には `df.head(2)` を返す | Accepted 4/4 | 指定名の存在確認だけでは、ilocの利用を検証できない |

再現用の主要例：

```python
# PY02-06：出力は合うが、指定の内部関数と辞書展開を使わない
def solve(config):
    return [v * config.get('factor', 1) for v in config['values']]

# PD04-06：指定された一意性検証を行わない
def solve(left, right):
    return left.merge(right, on='id', how='left')
```

**別解を禁止することが目的ではない。** 「この処理をすればよい」という動作の契約と、「このAPI・構文を使う」という練習の契約を分け、何を合格で示すかを明確にすることが目的である。

## 7. 改善の推奨順序

重要度と実装順は同じではない。学習の契約を先に定め、その契約に沿って表示と採点を揃える。

| 順序 | 対象 | 具体的な到達点 |
|---|---|---|
| 1 | UX01・08・09 | 初回に編集箇所と答え方が分かる。実行不可を事前に知る。未提出か保存済みか、終了まで一貫して分かる |
| 2 | UX03・04・14 | 入力・期待値・実値の構造を比較できる。前回結果／中止／現在コードの結果を区別できる |
| 3 | UX02・06 | 15問を先行して、動作契約・API練習・予測・バグ修正を整理し、文と採点を一致させる |
| 4 | UX05・11 | 先行15問のヒント・誤り例・解説を個別に書き直し、その基準を残り165問へ展開する |
| 5 | UX07・10・12・15 | 前提順の初回導線、空の復習、ヒント後の再挑戦、ステージの意味を整理する |
| 6 | UX13・16・19 | コードを戻す操作、Reading再開、履歴からの復習を整える |
| 7 | UX17・18・20 | 本文の可読性と狭い画面を調整し、学習に関係する情報を優先してコピー・装飾を削る |

文字の大きさなど低コストな改善は前倒しできる。ただし、情報の欠落を配色やカード形状の変更で代替しない。

### 教材の説明構造のひな形

各問を、次の順に読めるようにする。必要な内容をすべてカードに分けるのではなく、読む流れを揃える。

1. **今回すること**：入力に対して行う変換を1文で。
2. **編集する場所**：空欄／関数内部／誤り箇所を探す、のどれか。
3. **入力**：引数の型・意味・shape・制約。利用可能なimport。
4. **返すもの**：型・shape・index保持等。printではなくreturn。
5. **小さな具体例**：手計算できる入力→途中状態→出力。
6. **正解条件**：値の比較、許容誤差、必要なAPI、入力変更の可否を必要な場合だけ。
7. **ヒント**：注目点→小例による手順→構文・APIの部分例。
8. **解説と誤り例**：なぜ成立するか、具体的な失敗例、別入力へ一般化する条件。

用語の説明は、例えば「shape＝各軸の要素数」「fit＝学習データから基準や係数を決める」のように、課題に必要な意味をその場で示す。長い用語集を別画面で読ませることだけを解決策にしない。

## 8. 実行・採点・履歴への影響と守る条件

| 改善群 | 実行・採点への影響 | 履歴・進捗への影響 |
|---|---|---|
| コピー、文字、バッジ、入出力の型別表示 | 原則なし。正規化データや許容誤差は変えない | 内部ID・版・判定は保持 |
| 公開ケースの実値比較 | Resultの任意項目追加や公開比較情報が必要 | 古いResultに新項目がなくても表示可能にする |
| 提出して次へ、終了の要約 | 現在コードと実行結果の一致、送信の冪等性を維持 | RunとAttempt、未提出と提出済みを混ぜない |
| 利用不可表示 | runtime可否・失敗と学習者の誤答を区別 | 環境エラーで習熟度を下げない |
| ヒント・解説・誤答例の改稿 | APIの要件や例の値が変わらなければ主に教材変更 | 旧閲覧フラグを維持。新しい独力確認は新itemで実施 |

| 予測専用回答形式 | solve形式から変えるならスキーマ・採点経路に影響 | コード以外の回答を保存・表示できる設計が必要 |
| 選題・導入・再挑戦 | 新規キューに影響 | 進行中キューと下書き、復習日程を保持 |
| Reading復元・履歴検索 | 実行には原則影響なし | ActivityProgressとDrillのAttemptを区別し、提出時の版の名称を表示 |

版管理は既存の [content.py](../apps/api/app/content.py#L11) にあるVERSIONSと `content/versions/` の保存方式を活用する。公開例、解説、ヒント、模範コード、非公開ケースを含めて旧版を再現できることを確認する。現行の `update_learning` はベースIDからPROBLEMSを参照するため、ステージや形式を変える際は旧版提出の扱いも点検する。seed42／99の再現性も含める。

変更後の確認では、少なくとも次を扱う。

- 公開ケースの差分表示が非公開データを含まないこと、配列shape・Pandas index・必要なdtype・欠損値・許容誤差の比較が従来どおりであること。
- RunだけではAttemptを増やさず、提出の再送で重複せず、編集中・中止中・古い結果から誤って提出しないこと。
- ヒントあり／なし、模範解答閲覧、暫定／正式の区別とステージ条件を維持すること。
- エラー、次問移動、再読込、初期コード復元で下書きが失われず、競合時に無条件で上書きしないこと。
- 過去版の提出コード・結果・問題文を開け、既存の進捗と復習予定が勝手に再計算されないこと。

Pyodideの各実行を新しいWorkerで隔離する現在の方針も維持したい。今回、NumPyの実行は画面操作込みで約3.9〜7.6秒、表示された計算時間は約46〜66msだった。環境・ライブラリの準備時間と計算時間は違い、画面には準備中の説明が既にある。待ち時間の許容度は未測定なので、これを重大な速度障害とは計上していない。改善するならロード表示・キャッシュを先に検討し、学習者コードの状態を次の実行へ残す方式にはしない。

## 9. ユーザーテストで確かめる仮説

まずはPythonの関数・リストは書けるがNumPyや機械学習に不慣れな5〜6人程度で、探索的に確認する。人数は調査の提案であり、母集団の成功率を推定する規模ではない。司会者は操作方法を教えず、分からない語や次に押そうとした箇所を記録する。

| 課題 | 検証したい仮説 | 観察すること |
|---|---|---|
| 初回訪問から1問解き、記録を残して終える | UX01・07・09・20：開始点と完了の意味が伝わりにくい | 最初の行動までの時間、導線の戻り、実行／提出の選択、終了後に履歴を自分で確認できるか |
| NP05-01で軸を誤った状態から修正する | UX03〜05：判定だけでは修正根拠が得られない | 実際の出力の説明、ヒントの段階、修正後にaxisの意味を説明できるか |
| PD01-01で値は同じだがindexの違う結果を直す | UX03・04：見えない採点条件が障害になる | 採点される属性を認識できるか、期待値と自分の結果を比較できるか |
| 予測問題を解く | UX06：固定の値を答えるのか汎用関数を書くのかが曖昧 | 課題を自分の言葉で説明できるか、不要なファイル操作や再実装を始めるか |

合格したかだけでなく、「なぜそのコードになるか」「どの条件を満たしたか」を説明してもらう。装飾の好みの質問だけで判断せず、行動の記録と結び付ける。今回の監査から成功率や離脱率の数値は得ていない。
